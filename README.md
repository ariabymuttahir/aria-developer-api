# ARIA Developer API 🔌

ARIA's **own** API key system — like OpenAI's platform, but for ARIA.
Developers get a key like `aria_sk_...` and call ARIA's AI over an
OpenAI-compatible HTTP API. The server routes each call through your
provider chain (Gemini → DeepSeek → Mistral → OpenAI).

```
Developer --(aria_sk_...)--> ARIA Developer API --(your keys)--> Gemini/DeepSeek/Mistral/OpenAI
```

## How it works

| Piece | Where | Notes |
|---|---|---|
| Key issuance | Admin panel → **Developer API** page | Owner login; key shown **once** |
| Key storage | Firestore `developer_keys/{sha256}` | Only the **hash** is stored — raw keys can never be recovered |
| Usage | Firestore `developer_usage/{hash_YYYY-MM-DD}` | Per-day requests, tokens, errors, provider split |
| AI | `POST /v1/chat/completions` | OpenAI-compatible request/response |
| Auth | `Authorization: Bearer aria_sk_...` | Per-key daily quota + 60 req/min burst guard |
| Admin API | `POST/GET /admin/keys`, `/admin/usage`, `/admin/config` | Firebase owner ID-token (panel) or `x-admin-secret` |

Models: `aria-1` (auto chain), `aria-gemini`, `aria-deepseek`, `aria-mistral`, `aria-openai` (pinned).

## Run locally

```bash
cd ~/workspace/aria_api
npm install
# test mode: no real providers, no Firestore, no keys needed
ADMIN_SECRET=my-local-secret PROVIDER_MODE=stub STORE=memory PORT=8787 node src/server.js
```

Then in another terminal:

```bash
# 1. issue a key (admin)
curl -s -X POST localhost:8787/admin/keys -H "x-admin-secret: my-local-secret" \
  -H "Content-Type: application/json" \
  -d '{"name":"test","tier":"free","quotaDaily":100}'
# -> {"key":"aria_sk_...","label":"aria_sk_abc…", ...}   (copy the key!)

# 2. chat
curl -s -X POST localhost:8787/v1/chat/completions \
  -H "Authorization: Bearer aria_sk_..." -H "Content-Type: application/json" \
  -d '{"model":"aria-1","messages":[{"role":"user","content":"Hello ARIA!"}]}'

# 3. usage
curl -s localhost:8787/v1/usage -H "Authorization: Bearer aria_sk_..."
```

## Deploy to Render (public URL) — ~10 minutes, one time

You need a free [Render](https://render.com) account.

**Option A — Blueprint (easiest):**
1. Push this folder to a GitHub repo (e.g. `aria-developer-api`).
2. Render dashboard → **New → Blueprint** → connect the repo. `render.yaml` is picked up automatically.
3. In the service's **Environment** tab, set:
   - `FIREBASE_SERVICE_ACCOUNT_JSON` — whole service-account JSON on one line. Get it from Firebase Console → Project settings → Service accounts → Generate new private key. (This lets the server use your real Firestore, verify owner logins, **and read your provider keys from `config/api_keys`** — so you do NOT need to paste provider keys here.)
   - `PROVIDER_MODE` — **delete it / leave empty** (stub is local-test only!).
   - `ADMIN_SECRET` is auto-generated by the Blueprint.
   
   > The server reads your AI provider keys (Gemini, DeepSeek, Mistral, OpenAI)
   > straight from Firestore `config/api_keys` — the ones you already saved in
   > the admin panel. Rotate them in the panel anytime; the API picks them up
   > within ~5 minutes. Only set `GEMINI_API_KEY` etc. as env vars if you want
   > to override the panel.
4. Deploy. Your public URL will be like `https://aria-developer-api.onrender.com`.

**Option B — manual:** Render → New → Web Service → Docker → point at the repo; same env vars.

**Then:** open the ARIA admin panel → **Developer API** page → paste the public URL → Save → Test Connection → issue your first real key.

> 💸 **Cost warning (important):** every developer API call burns **your** provider
> quota/credits. Gemini's free tier is generous; DeepSeek/OpenAI are pay-per-use.
> Keep per-key daily quotas tight (default 100), issue keys only to people you
> trust at first, and watch the Usage card. Render's free tier sleeps after
> inactivity (first call takes ~30s to wake) — the $7/mo Starter plan stays awake.

## For developers (give them this)

**Base URL:** `https://YOUR-RENDER-URL/v1` — OpenAI-compatible. Any OpenAI SDK works; only the base URL + key change.

```bash
curl https://YOUR-RENDER-URL/v1/chat/completions \
  -H "Authorization: Bearer aria_sk_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"aria-1","messages":[{"role":"user","content":"Hello ARIA!"}]}'
```

```python
from openai import OpenAI
client = OpenAI(base_url="https://YOUR-RENDER-URL/v1", api_key="aria_sk_YOUR_KEY")
r = client.chat.completions.create(model="aria-1",
    messages=[{"role": "user", "content": "Hello ARIA!"}])
print(r.choices[0].message.content)
```

- `GET /v1/models` — available models (no auth needed).
- `GET /v1/usage` — your key's quota + today's usage (Bearer key).
- Limits: daily quota set by the owner (default 100/day), 60 requests/minute. No streaming in v1.

## Security model

- Raw keys exist only at issuance (shown once) and in the developer's hands.
- Server stores SHA-256 hashes; Firestore rules deny **all** client access to `developer_keys` / `developer_usage` (see `~/workspace/aria_ai/firestore.rules`).
- Provider keys are env vars on the server — never in the app, never in Firestore client-readable docs.
- Logs record only key labels (`aria_sk_abc…`), never key material.
